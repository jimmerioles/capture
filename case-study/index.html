01

The problem

Every screenshot tool starts by leaving the page.

The OS shortcut opens a markup window. The extension asks for permission to read every tab. The upload service wants the image on its server before it can be annotated. The page is always the input, never the tool.

That split is familiar, and it costs three things. The pixels are often captured at display resolution. The markup happens in another context. And the file usually takes a detour through a second app or someone else’s storage.

Capture starts from a different premise. The page already has a renderer, pixels, a clipboard, and a download path. It can do the whole job itself.

  • OS capture. Fast and universal, but the edit happens in a separate window, and the result is a file you now have to manage.
  • A browser extension. One click and the viewport is yours, at the cost of a permission surface and, usually, a separate editor.
  • Upload and annotate. Good for sharing and collaboration, but the image leaves the machine before the first arrow is drawn.

Each one treats the page as input. Capture treats the page as the camera.

A different place to do the work.

The comparison is not about features. It is about where the pixels live and who holds them.

02

The idea

A demo that can see itself.

The subject is Northstar, a fictional analytics app drawn entirely with Canvas 2D: cards, charts, type, the pulsing endpoint, all of it.

The demo is not a screenshot of an app. It is a live drawing, repainted roughly thirty times a second. That matters because the shutter copies the actual backing store. The capture is not a re-render or a reconstruction. It is the same pixels the browser just painted.

Then the stage changes jobs. The live layer fades, the frozen bitmap takes over, and the toolbar appears on the same rectangle. There is no mode switch to another screen, no file picker, no upload. The page is the subject, the camera, and the editor.

The premise

The demo is the subject. The capture is real.

This is the part that is hard to fake in a mockup. The tool is not describing a capture workflow. It is running one.

The app is deliberately small: four TypeScript modules, one HTML file, one stylesheet, no runtime framework. The interesting part is not the amount of code. It is where the pixels come from.

How it works

The freeze is the architecture.

There is no server, no scene graph, and no second copy of the interface. Four moves carry the whole prototype.

01 Live canvas PreviewRenderer, ~30 fps, up to 2.5×
→
02 Frozen bitmap Offscreen copy at backing-store size
→
03 Export canvas Frozen image plus marks, cropped
→
04 PNG Clipboard or local download
  1. 01

    The preview is code.

    PreviewRenderer paints Northstar with Canvas 2D. It targets roughly 30 fps, pauses when the tab is hidden or the station leaves the viewport, and renders a static frame under reduced motion.

  2. 02

    The shutter copies the backing store.

    startCapture() refreshes the preview, stops the loop, and passes the live canvas to the editor. The editor copies it into an offscreen canvas at the full backing-store size. No DOM is rasterized and no pixels are re-rendered.

  3. 03

    Selection and marks are fractions.

    The rectangle and every mark are stored in normalized 0 to 1 coordinates. The display canvas composites the frozen image, a dimming veil, the bright cutout, the marks, and the selection chrome. Resize the stage and the geometry still lines up.

  4. 04

    Export starts from the source.

    buildExportCanvas() paints the frozen bitmap and the marks into a clean canvas at native resolution, crops to the selection if there is one, and returns it. Copy and Download encode that canvas. The screen composition is never the source.

The copy and the export

// Copy the live backing store into the frozen bitmap.

  this.frozen.height = source.height;
  this.frozenCtx.drawImage(source, 0, 0);
  this.captureScale = this.frozen.width / this.stage.clientWidth;
}

// Paint the source and the marks, then crop to the selection.
const png = editor.buildExportCanvas();

The stage chrome reports the backing-store size and the effective DPR. The frozen image stays intact while the live layer is hidden, which is why the editor can survive a resize without recapturing.

05

The marks

Three marks, drawn from the pixels underneath.

Arrow, box, and pixel blur. Each one is geometry, not a baked-in edit, so it redraws at any size and in the export.

The arrow and the box are strokes with a dark halo under an ice line, so they read over bright and dark captures. The blur is not a CSS filter over the live app. It downsamples the selected region of the frozen bitmap into a small grid, then scales it back with smoothing off. The mosaic can only reveal pixels that are already in the capture.

Because the marks live in normalized space, they survive a resize and they scale to the source bitmap at export. The display composition and the file composition share the same geometry.

What each mark is made of.

Arrow
2.4px ice stroke over a 5.4px dark halo, round caps
Box
2.1px stroke with a 5.5 percent fill and a 2.5px radius
Blur
2 to 90 cells per side sampled from the frozen bitmap, not the screen

Performance

Nothing moves until something changes.

The preview is an ambient loop, not a game. It runs at about 30 fps, stops when it is not visible, and stops again when the shutter fires.

During a capture the loop stops before the copy, so the frozen frame and the live frame cannot disagree. The export is a synchronous composite over one bitmap. There is no network request in the path.

The film’s clock chapter follows the same rule: one requestAnimationFrame pulse feeds the endpoint, the LIVE dot, and the chart scan. Hide the tab or scroll the station away and the pulse stops. Freeze the image and the clock stops with it.

The numbers here are design constants and budgets from the build, not a published benchmark. A frame trace on a mid-range laptop is still to come. The target is a steady 30 fps preview and a capture that finishes inside one interaction, with no long task over 50 ms.

07

Accessibility

Every control is a real control.

The canvas is the picture. The interface around it is ordinary HTML, and the keyboard path is not an afterthought.

  • Buttons, not divs. The shutter, toolbar, Copy, Download, Reset, and Exit are buttons with names. The toolbar takes ArrowLeft, ArrowRight, Home, and End. Focus moves to the snapshot after a capture.
  • The shortcuts have equivalents. C captures. V, A, R, and B choose Select, Arrow, Box, and Blur. Esc exits. Every key has a visible control.
  • The live region narrates. Captures, selection sizes, marks, clipboard results, and exits are announced. The preview canvas has a role and a name, and the snapshot is labeled and focusable.
  • Motion is optional. Reduced motion removes the flash, the stage kick, and the entrance animations. Every tool still works, and the freeze becomes a fade.
  • Sound waits for intent. The shutter and chime are synthesized with Web Audio inside a user gesture. Mute is remembered. Nothing autoplays.
  • The phone layout holds. At 390 × 844 the stage stacks, the toolbar becomes icon-only, and touch dragging still works. Every tool is still reachable.

08

Limitations

What this does not claim.

A prototype is more convincing when it says where the edges are. These are the current ones.

  • It captures its own canvas, not the full page or the operating system. That limit is the reason the demo is honest and the reason it is not a general screenshot tool yet.
  • There is no per-mark undo. Reset discards the whole capture.
  • Text callouts, movable annotations, and color choices are not implemented.
  • Resizing during a capture stretches the frozen bitmap to the new stage aspect. The geometry survives; the pixels do not.
  • Copy needs the Async Clipboard API and a secure context. When the clipboard blocks an image write, Copy downloads the PNG instead and says so.
  • There is no automated test suite yet. npm run build runs the TypeScript check.
  • The film is finished. The product’s in-page guided tour is not.
09

What is next

The next version should close the distance to a real tool.

The prototype has proven the interaction. The remaining work is resilience, range, and evidence.

  1. 01

    Undo and selectable marks

    A per-mark history, with the ability to move or delete one mark without resetting the capture.

  2. 02

    Text and color

    Short callouts and a small palette, without turning the toolbar into a design app.

  3. 03

    A full-page path

    Capture a taller surface than the stage canvas, then keep the same normalized editor. This is a different compositor, not a CSS tweak.

  4. 04

    A real share sheet

    The Download link is a placeholder today. Replace it with a desktop handoff or a save flow that matches the local promise.

  5. 05

    A test suite

    Cover normalized geometry, crop bounds, export size, keyboard behavior, and the clipboard fallback.

  6. 06

    A frame trace

    Measure paint counts and frame pacing on a mid-range laptop, then publish the numbers beside the current budgets.
